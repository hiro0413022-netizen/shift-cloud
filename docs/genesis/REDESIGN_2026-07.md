# REDESIGN 2026-07 — 「報告システム」から「自律実行OS」へ

> ステータス: **設計案（ユーザー承認待ち）**。承認後に DECISIONS へ採番し実装開始。
> 発端: 古川さんの指摘（2026-07-24）「情報量が多すぎて見にくい。報告システムになっている。理想はAIが改善して自動で動く仕組み。営業も自動でこなす」

---

## 1. 診断 — なぜ「報告システム」になったか

- サイドバー **26画面**。うち大半が「AIの活動を人間が読むためのページ」（改善提案 / 実行指示 / 承認待ち / 成果物レビュー / 出来事ログ / 決定事項ログ / 開発状況 …）。
- 判断の入口が **5か所に分散**（/approvals・/suggestions・/directives・/deliverables・/inbox）。どれも「読む→別画面へ移動→操作」で、VISION §1 の「判断すべきこと3つだけ」と真逆。
- 自律実行の土台（#61〜63: `ai_execution_policies` 3階層・executor・`ai_action_queue`）は**本番稼働済み**だが、外部送信は全て approval に退避中＋実チャネル実送信が未接続。さらに **「実行した結果どうなったか」を測る仕組みがない** ため、AIは提案を積むだけで学習ループが閉じていない。

**結論: 足りないのは新機能ではなく、(a) 画面の大胆な集約 と (b) 観測→実行→測定のループを閉じること。**

## 3. 新しい画面構成（26 → 5＋管理）

1. **全体スコア＋一言サマリ**（CEO AIの今日の要約1〜2文）

   - AI実行の承認待ち・取消枠（ai_action_queue）
   - 成果物レビュー（ai_execution_logs）

4. **AI活動ティッカー**（直近の自動実行を1行×5件。詳細はAI社員ページへ）

現行トップの「改善提案パネル」「リスク/承認/イベント3カラム」は判断フィードに吸収 or 管理へ。

### 3-2. チャット `/chat`

### 3-4. 数字 `/finance`

## 4. 自律ループ設計（第一弾: 営業＋スタッフ指示）

共通形: **観測 → 判断 → 生成 → 実行（ポリシー準拠）→ 測定 → 学習**。新テーブル `gn_loops`（ループ定義）＋ `gn_loop_runs`（各サイクルの観測値・打ち手・結果）を追加（migration番号は実装時に採番）。

### 4-1. 営業AIループ「体験予約を目標に到達させる」
| 段階 | 内容 |
|---|---|
| 観測 | 体験予約（mbr_trial_bookings / mbr_trial_requests）の当月ペース vs 目標、休眠会員、8月値上げ駆け込み余地 |
| 判断 | 不足検知 → 打ち手選択（掘り起こしLINE / 体験キャンペーン / 駆け込み訴求）。しきい値・頻度上限（例: 同一顧客30日1回）をループ定義に保持 |
| 生成 | LINE配信文・キャンペーン案を成果物として自動生成（既存 agent-runner 流用） |
| 実行 | **approval 維持**: ホーム判断フィードにワンタップ承認カード → 承認で gn_line_outbox → n8n 実配信（既存 #59 経路） |
| 測定 | 配信後7日間の体験予約数・LINE反応を loop_run に自動紐付け |
| 学習 | 結果を CEO AI 日次に注入（「先週の掘り起こしLINEで体験+3件」）→ 次回の打ち手選択に反映 |

### 4-2. スタッフ指示ループ（既存強化）
- CEO AI 日次の staff_directive（朝連絡）は現行どおり approval だが、**ホームの判断フィードでワンタップ承認**に。
- 承認後の配信結果（既読/完了 sp_tasks）を翌日の CEO AI が観測 → 未完了タスクの再指示を自動生成。

### 4-3. やらないこと（今回スコープ外）
- 外部送信の auto_undo 化（試運転の結果を見て別途判断）
- SNS実投稿・在庫発注ループ（第二弾）
- 既存テーブルのリネーム・破壊的変更

## 5. 全システム連携（Genesisをハブに）

現状: 全アプリが同一Supabaseを共有しているのに、**判断の入口がアプリごとに分散**している（member-os「体験申込」/ FRANK会員承認 / reserve-os「予約確定」/ Genesis inbox …）。古川さんが巡回しないと止まる構造。

**(a) 横断判断フィード** — ホームの判断フィードに他アプリの承認系を吸収:
- 体験申込の日程確定（mbr_trial_requests）
- Web入会の承認＝会員番号発行（frunk_members pending）
- ビジター予約の確定（res_requests）
- DB共有のため新API不要。Genesisが既存テーブルを直接読み書きし、各アプリと同じstatus更新＋通知を行う。詳細操作が要るときだけ各アプリへ深リンク。

## 6. 開発自律化 — pushもデプロイもGenesis画面から

現状: push自動化(2026-07-14開通)とVercel MCPは揃っているが、**prod_deployハンドラが未配線**（NEXT_TASKS C-0d）で、デプロイの起点がチャット/ユーザーPCに残っている。

**開発AIループ:**
| 段階 | 内容 |
|---|---|
| 観測 | 改善提案・バグ（Sentry接続済）・ホームからの改善要望 |
| 生成 | 開発AIが実装 → **tsc＋tests通過をデプロイカードの前提条件に**（CIゲート） |
| 実行 | ホームに「デプロイ承認」カード（変更概要・影響範囲・テスト結果つき）→ ワンタップ → prod_deployハンドラが git push ＋ Vercelデプロイを実行 |
| 検証 | デプロイ後ヘルスチェック（主要URL 200・Sentryエラー率）。失敗時は**前回デプロイへ自動ロールバック**し、結果をティッカーへ |
| 学習 | デプロイ履歴・失敗要因を開発AIの観測に戻す |

DBマイグレーション（db_change）は引き続き**内容表示つきの個別承認**。古川さんの開発関与は「ホームでワンタップ」だけになる。

## 9. UI設計指針（2026-07-24 追記）

1. **1カード=1判断**。タグ（どのAIか）＋タイトル＋予測効果1行＋大きな承認/却下ボタン。文面・対象一覧はカード内で展開（画面遷移ゼロ）。
2. **色は状態にだけ使う**: 赤=判断必要 / 黄=注意 / 緑=順調。現行のHUD風装飾（グロー・blink・ネオン）は撤去し「0.5秒で読める」を優先。数字は大きく、ラベルは小さく。
3. **スコアは前日比＋要因1行**。点数単体では判断材料にならない。
4. **モバイル最優先**: 下タブ5つ（ホーム/チャット/AI社員/数字/管理）。判断カードは縦積み・承認ボタンは親指圏（画面下寄せ）。朝の承認はスマホで完結する前提で設計。
5. **ゼロ状態を誇る**: 判断0件の日は「今日の判断はありません。AIが回しています＋昨日AIがやったこと3行」。目指す状態（人が要らない日）を可視化する。
6. **承認後の取消チップ**: 承認直後にカードが消えず「送信予定 12:00・取り消す」に変わる（auto_undoの取消枠と同UI）。
7. **Cmd+K コマンドパレット**: 管理配下に格下げした全画面・スタッフ・会員をインクリメンタル検索で即ジャンプ。サイドバーを増やさない逃げ道。
8. **表示速度1秒以内**: ホームの集計は並列fetch＋短TTLキャッシュ。遅い集計はスケルトン表示ではなく前回値＋更新時刻を出す。

## 11. 成功の定義

- 朝ホームを開いて **30秒以内に今日の判断が終わる**（判断フィードで完結）
- 営業AIが人の起案なしで「不足検知→LINE文→承認待ち」まで自動で並べる
- 配信の翌週、「打ち手→結果」が数字で見える（loop_runs）
- 体験申込・入会承認・予約確定など**全アプリの判断がホーム1か所で終わる**（アプリ巡回ゼロ）
- 開発〜デプロイが**古川さんのPCなしで完結**（関与はホームのワンタップのみ、失敗時は自動ロールバック）
