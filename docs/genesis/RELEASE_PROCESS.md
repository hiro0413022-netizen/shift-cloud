# RELEASE_PROCESS — リリース分離と修正フロー（外販の土台）

作成: 2026-08-23（ユーザー決定にもとづく）。外販開始にあたり「自社の毎週の改修が顧客の本番を壊す」事故を構造的に防ぐ。

## 1. 2つのチャンネル

| ブランチ | 役割 | 誰が使う | 更新頻度 |
|---|---|---|---|
| `main` | **開発版**。自社店舗（GOLF WING / FRANK GOLF）が使う | 自社 | 従来どおり毎週・随時 |
| `release` | **安定版**。外販顧客のシステムはすべてここから配信 | 外販顧客 | **月1回の昇格＋緊急バグ修正のみ** |

- 外販顧客向けVercelプロジェクトは **Production Branch を `release`** に設定する（新規作成時に必ず。Settings → Git → Production Branch）
- 自社向け既存プロジェクト（shift-cloud / genesis / member-os 等）は `main` のまま
- **顧客への機能追加は月1回**。バグ修正だけは即日 `release` へ流す

## 2. 月次昇格（毎月1回・約15分）

1. GitHub で `main` → `release` の Pull Request を作る（タイトル例: `release 2026-09`）
2. CI（テスト＋全アプリbuild）が緑であることを確認
3. 差分を目視（migration が含まれる場合は §4 を確認）
4. マージ → 顧客向けVercelが自動デプロイ → 顧客テナントでスモーク（ログイン・予約作成・体験受付の3操作）

## 3. 緊急バグ修正（hotfix）

顧客側で不具合が出た場合のみ。機能追加はこの経路を使わない。

1. `release` からブランチを切る: `git checkout release && git checkout -b hotfix/説明`
2. 修正 → PR を **`release` 宛て**に作成 → CI緑 → 古川さんがマージ
3. 同じ修正を `main` にも取り込む（cherry-pick か、次回昇格時に自然合流するなら省略可。**省略した場合はPR本文に明記**）

## 4. migration の規律（顧客DBを壊さないために）

- `release` に入る migration は**後方互換のみ**: 列追加は nullable / DEFAULT つき、テーブル追加はOK。**列削除・型変更・RENAME は不可**（旧デプロイが動かなくなる）
- 削除系はフェーズ分割: ①新列追加と両対応コードを昇格 → ②翌月以降に旧列を落とす
- 昇格PRに migration が含まれる場合、マージ前に Supabase へ適用する（コードより先にDB）

## 5. 修正フロー（山本さん＝レベル2 の作業ルール）

山本さんはAI（Claude Code）を使ったコード修正が可能。ただし**直接pushはしない**。

1. 作業はブランチで: `git checkout -b fix/説明 origin/main`
2. push して **PR を `main` 宛て**に作成（テンプレートに従う）
3. CI が緑になるのを待つ（赤のままレビュー依頼しない）
4. **古川さんが承認してマージ**（Merge は古川さんのみ）
5. 顧客に届くのは次回の月次昇格（緊急なら §3）

権限の線引き（2026-08-23決定）:
- 山本さん = 設定・データ・コンテンツの変更、一次サポート、コード修正のPR作成まで
- 古川さん = PRの承認とマージ、本番DBの変更、`release` への昇格・hotfix

## 6. 重大障害の定義とSLA（顧客向けの約束）

- **重大障害** = 予約・決済・入会のいずれかが顧客店舗で機能停止 → **夜間休日を問わず即時対応（古川さん）**
- それ以外 = 営業時間内の対応（一次受付はAIが24時間）
- SLAの文言: 「一次応答は即時（AI）、通常対応は営業時間内、重大障害は即時に担当者が対応します」

## 7. GitHub 側の設定（初回のみ・ユーザー作業）

1. `release` ブランチの作成（下のコマンド）
2. Settings → Branches → Add branch protection rule:
   - Branch name pattern: `release`
   - ☑ Require a pull request before merging
   - ☑ Require status checks to pass（`test` と `build` を選択）
   - これで release への直接pushが構造的に不可能になる
3. （任意・山本さんの直接push防止）`main` にも同じルール＋ "Allow specified actors to bypass" に古川さんのアカウントを追加すると、古川さんは従来どおり直接push・山本さんはPR必須にできる

## 8. なぜこうするのか（決定の記録）

- 一番の障害原因は外部障害ではなく**自分たちのデプロイ**。現状はmainへのpushが全プロジェクトへ即時反映される
- 「毎週直せる」は自社の強み。顧客には「昨日と同じように動くこと」が価値。この2つを両立する唯一の方法がチャンネル分離
- トレードオフとして顧客への機能追加は月1になる（バグ修正は即日）。これは意図した仕様
