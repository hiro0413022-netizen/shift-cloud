# FRANK GOLF｜会員QRチェックイン 構想まとめ（開発前・2026-08-26）

## 0. 一行でいうと

**チェックインは目的ではなく「来店したらスマホを開く」という習慣を作るための入口。**
入口を作るだけなら小さい開発だが、開いた先に何を置くかで価値が決まる。

---

## 1. やりたいこと（ご意向の整理）

- 会員が入会したら、その会員専用の **QRコード（またはバーコード）** を発行する
- 来店時、お客様は **スマホでQRを表示 → 受付のリーダーにかざす → チェックイン完了**
- 受付には **PC＋USB接続のQRコードリーダー** を置く
- **本当の狙い＝スマホを開かせること。** チェックインのためにスマホを開くと、そのついでに
  - ドリンクオーダーができる
  - レッスンコメント（カルテ）が確認できる
  - 次回予約・お知らせが目に入る
  という導線が自然に生まれる。「来店＝スマホを開く」を習慣化したい。
- 副次的に、スタッフの手間が減る（来店確認・キャンセル/無断欠の確認が自動になる）

---

## 2. 現状（すでにあるもの／足りないもの）

### すでにあるもの＝流用できる

| ある | 中身 | チェックインでの役割 |
|---|---|---|
| **会員マイページ `/member`** | 会員番号＋電話下4桁でログイン、cookie 60日保持。予約一覧・キャンセル・カルテリンクを表示済み | **QRを置く場所。ここが「開くスマホ画面」の本体** |
| **予約台帳 `frunk_bookings`** | ステータスに `visited`（来店）／`no_show`（無断欠）が既にある。今はスタッフが手で押している | チェックインで**自動で `visited` に**できる |
| **受付台帳 `mbr_walkin_visits`** | 体験は予約が入った瞬間に自動反映済み | 来店KPIの受け皿 |
| **Lesson OS カルテ `/s/<token>`** | マイページから既にリンク済み | 「開いた先」の中身が1つ完成している |
| **Square POS** | ドリンク24品を**一般／会員の2バリエーション**で登録済み。スタッフ打ち運用で確定 | ドリンク注文の会計側 |

### 足りないもの＝今回作る

- 会員QRの発行と表示（マイページ内）
- 受付のチェックイン画面（フルスクリーン・読むだけで完結）
- チェックイン記録テーブルと、予約との自動照合
- 「来店中モード」＝滞在中だけ出るスマホ画面（ドリンク注文・カルテ・打席）
- **ハード：USB QRリーダー、受付PC**（買い物が先）

## 3. 仕組みの案

### A. QRの中身 ─ ここが一番大事な判断

| 案 | 中身 | 良い点 | 弱い点 |
|---|---|---|---|
| ① 固定QR | 会員番号（F0001）をそのままQRに | 一番簡単。印刷した会員証カードにもできる | **スクショで済んでしまう＝スマホを開かない**。他人に渡せば会員価格が使える |
| ② **回転トークン（推奨）** | 30秒ごとに変わる署名付きトークン（TOTP方式）。マイページを開いている間だけ有効 | **開かないと入れない＝習慣化の目的そのもの**。使い回し・なりすまし不可 | 実装が少し増える（といっても数十行）。電波が無いと表示できない→対策必要 |
| ③ 期限付き署名QR | 1日有効の署名。毎朝作り直し | 中間 | 中途半端（スクショで1日使える） |

**推奨は②。** 理由は単純で、今回の目的が「来店したらスマホを開く」ことだから、
**スクショで代替できてしまう設計は目的を殺す**。
※オフライン対策として、②が表示できない時のために「会員番号を口頭で伝える」手動チェックインは必ず残す。

### B. 受付側の読み取り ─ **機種確定：Tera 9200（2026-08-26 購入済み）**

USB有線・卓上式・360°全方位・自動検知・1D/2D・液晶画面読取対応。**要件を満たしています。**

**この機種だとこうなる（設計に効く4点）**

1. **USB HIDキーボードとして動く。** PCから見ればただのキーボードで、読み取った文字列をそのまま「打つ」。専用ドライバもSDKも不要 ＝ **受付PCは Web画面を開いて入力欄にフォーカスを当てておくだけ**でいい。実装は最小。
2. **卓上＋自動検知＝スタッフが持たなくていい。** かざせば勝手に読む。つまり **お客様が自分でかざすセルフチェックイン台**にできる。当初案（スタッフが読み取る）より一段良く、スタッフの手間はゼロになる。カウンターの客側に置く前提でレイアウトを考える。
3. **⚠ キーボード配列の罠 → トークンの文字種を先に縛る。** 既定はUS配列で送信されるため、日本語配列のPCに繋ぐと**記号が化ける**（`-` `/` `_` `\` など）。設定バーコードで日本語配列に変えることもできるが、機種設定に依存させたくない。
   → **QRトークンは「数字＋英大文字」だけで作る（記号なし・小文字なし）。** こうすれば配列設定が何であっても絶対に化けない。**これは実装前に確定させる仕様。**
4. **末尾にEnterを付ける設定を入れる。** 付属の設定バーコード（Suffix = CR/Enter）を1回読ませれば「読み取り＝送信」になり、スタッフのキーボード操作がゼロになる。

**運用上の注意（卓上・常時待機ゆえ）**

- 何か置くと勝手に読むので、**商品バーコードや他店のQRを誤読する**。受付画面側で「自社トークンの形式でなければ無視する」判定を必ず入れる。
- スマホ画面から読ませるので、お客様には**画面輝度を上げてもらう**案内が要る（保護フィルムの反射で読めないケースあり）。マイページのQR表示中は**自動で輝度を最大にする**実装も可能。

---

### B-2. 受付PCを「チェックイン専用」にはできない ─ 兼用問題の解き方

**当初「受付PCは他の作業に使わない（キオスク運用）」と書いたが、これは撤回する。**
現場ではメール確認・予約確認をその場でやりたい。運用ルールで縛る設計は必ず破れる。

そして兼用にはもう一つ、より重い問題がある。
**セルフでお客様にかざしてもらうなら、画面はお客様側を向く。** そのままだと
**スタッフのメール画面・予約画面・他のお客様の情報が、来店客に丸見えになる。**
誤入力より情報の見え方のほうが問題として重い。

| 案 | 内容 | 評価 |
|---|---|---|
| **A. 端末を分ける（推奨）** | チェックイン専用端末（中古ノート2〜3万円／余っているPCで可）を**お客様側に向けて**設置。受付PCはスタッフ側を向いたまま自由に使う | **運用ルールが一切要らない**のが最大の利点。誤入力も情報漏れも構造的にゼロ。どのみちセルフにするなら客側を向いた画面が要る＝2画面は避けられない |
| B. 1台のまま・リーダーを「仮想COM」にする | 設定バーコードで **USB COMポート（仮想シリアル）** に切り替えられれば、キー入力として飛ばない＝メールを打っていても文字が混ざらない。チェックイン画面はChromeで開きっぱなしにし、Web Serial API で受信 → 読んだ瞬間に前面表示＋音 | **要確認：付属の日本語説明書に「USB COMポート／仮想シリアル／RS232」の設定バーコードがあるか。** あれば有力。ただし**画面がお客様に見える問題は残る** |
| C. 1台のまま・HIDのままソフトで横取り | トークンの先頭に固定の合図（例 `FRK`）を付け、常駐アプリがキー入力を監視して「合図で始まり人間では不可能な速度」のパターンだけ横取りする | 動くが、**常駐アプリという保守物が増える**。少人数の店で持つには重い。非推奨 |

**推奨は A。** 判断待ち。9/2までにPCを買い足したくない場合は B を検討するので、
**付属の説明書に仮想COM／RS232の設定バーコードがあるか確認してほしい。**

**配置の確認事項：** Squareリーダー第2世代は単体で動かず接続端末（スマホ/タブレット）が必要。受付には
「**チェックイン端末＋Tera 9200（客側向き）**」と「**受付PC（スタッフ側向き）**」と「**レジ端末＋Squareリーダー**」が並ぶ。
カウンターのレイアウトと**USBケーブル（約1.8m）の取り回し**を先に決めたい。

### C. かざした瞬間に起きること

1. **会員を特定し、今日の予約を照合**
   - 予約あり → `visited` に自動更新＋来店時刻を記録
   - 予約なし（フリー来店）→ 「予約なし来店」として記録（当日枠に自動で入れるかは要判断／§6-3）
   - 体験・ビジターはQRを持たない → 受付画面から手入力（今まで通り）
2. **受付PCに大きく表示**（3秒で消える）
   - 氏名・プラン・**打席番号**・⚠重要説明事項・未収金があれば警告
   - 個人情報は出しすぎない（生年月日・住所は表示しない）
3. **お客様のスマホが自動で「来店中」画面に切り替わる** ← ここが本丸
4. **データに反映**：来店実績KPI、無断欠の自動判定（予約時刻を過ぎてチェックインが無ければ）

## 4. 「開いた先」の設計 ─ ここで価値が決まる

チェックインは入口にすぎない。**開いた直後に何が出るか**を決めておかないと、
「かざすだけの作業」になって習慣にならない。

**来店中モード（滞在中だけ表示されるホーム）に置くもの：**

1. **ドリンク注文** — Squareカタログの会員価格で表示 → 送信すると受付PCに通知が鳴る
2. **今日のレッスンカルテ／前回のコメント** — Lesson OS 側は既にある。導線を繋ぐだけ
3. **本日の打席・残り時間**
4. **次回予約ボタン** — 帰る前に次を取らせるのが一番効く
5. **お知らせ／キャンペーン** — 期間限定を「開いたときに必ず目に入る」場所に置ける

**退店後**：自動でお礼メッセージ＋次回予約導線（LINE/メール・送信基盤はある）

## 5. ドリンク注文の会計（落とし穴）

**注文＝決済ではない。Squareのレジを通さないと Money OS に1円も載らない。**

| 案 | 内容 | 判断 |
|---|---|---|
| **a. 注文票だけ（推奨）** | スマホの注文は「オーダー伝票」。会計はスタッフがSquareで打つ（今の運用のまま） | **第一弾はこれ。** 実装が軽く、売上計上の仕組みを一切壊さない |
| b. スマホで先払い | Squareオンライン決済 | 手数料が**3.6%**（対面2.5%より高い）。会員価格の扱いも別設定が要る |
| c. 月末まとめ請求 | 月会費と一緒に | Squareサブスクとは別建てになり実装が重い。未収リスクも増える |

## 6. 開発フェーズ案

| Phase | 内容 | ざっくり工数 |
|---|---|---|
| **Phase 0（先に必要・ユーザー作業）** | ~~USB QRリーダー購入~~ **完了（Tera 9200・8/26）**／受付PCの決定／カウンター配置／リーダーの設定バーコード（Enter付与・配列） | 実機作業のみ |
| **Phase 1｜チェックインが動く** | マイページにQR表示（回転トークン）／受付チェックイン画面／来店記録・予約自動照合／手動チェックインの逃げ道 | 1セッション程度 |
| **Phase 2｜開いた先を作る** | 来店中モード（ドリンク注文＋カルテ＋打席＋次回予約）／受付PCへの注文通知 | 1〜2セッション |
| **Phase 3｜育てる** | 無断欠の自動判定／来店データのKPI・分析（頻度別・離脱予兆）／退店後フォロー自動化／体験・ビジター用の当日QR | 随時 |

**Phase 1 だけなら小さい。** ただし Phase 2 まで行かないと当初の目的（習慣化）は達成されない、という前提で計画したい。

## 7. 開発前に決めてほしいこと

1. **QRは回転式か固定式か** → 推奨は回転式（スクショ対策＝習慣化の要）
   ※文字種は Tera 9200 の都合で **数字＋英大文字のみ** に確定（§3-B-3）
2. **チェックイン端末を別に立てるか、受付PCと兼用するか（§3-B-2）** → 推奨は**別に立てる（案A）**。
   兼用だとスタッフの画面がお客様に見えてしまう。兼用でいくなら **仮想COM対応の確認**が先
   ※Tera 9200 は **USB有線**。タブレットだとUSB-Aの口とOTG給電の問題が出るので **Windows PC（ノートで可）**が確実
3. **予約なし来店（フリー来店）を許すか** → 許す場合、当日枠へ自動で入れるか／スタッフ確認を挟むか
4. **体験・ビジターもQRにするか** → 当日限りのQRをメールで送る、という形にできる（Phase 3）
5. **ドリンク注文の決済方式** → 推奨は「注文票だけ・会計はSquare」
6. **9/2プレオープンに載せるか、後追いか** → Phase 1 だけなら間に合う可能性はあるが、**レジ商品の未登録（ビジター/体験/レッスン単発/物販）や電子マネー申請のほうが先**

## 8. リスクと必ず作る逃げ道

- **お客様がログインできない／スマホを忘れた** → 受付画面から氏名・会員番号で検索して手動チェックイン（必須。これが無いと現場が止まる）
- **リーダー故障・PC不調・通信断** → 紙の来店記録に落とし、後からまとめて入力できるようにする
- **個人情報** → 受付PCの画面は人目に触れる。氏名・プラン・打席・注意事項までにとどめ、生年月日/住所/連絡先は出さない
- **過去の罠の再来防止** → 会員の導線を増やすときは、必ず `frunk_members` に入るか確認する（旧「仮会員 P########」は台帳に存在せず、Web登録した人が100%予約できなかった事故がある）
- **店舗スコープ** → UIで隠すのではなく、**サーバー側で store_id を検証**する（既存ルール）

---

## 9. 副産物として得られるデータ

チェックインが動くと、今まで取れていなかったものが自動で貯まる：

- 会員ごとの**来店頻度**（月何回来ているか）→ 退会予兆の検知（例：前月比で来店が半減）
- **時間帯別の混雑実態**（予約ベースではなく実来店ベース）→ スタッフシフトと打席の増設判断
- **予約→実来店率／無断欠率**
- ドリンクの**会員別購買**（客単価アップの余地）

これは Report OS / ダッシュボードにそのまま流し込める。
