## 2. モバイルオーダーの会計 ─ 「注文＝決済」で作る

### 2-1. 結論：技術的に可能。第一弾からこれでいく

Squareに**カード情報が保存されている会員**（＝月会費をカード払いしている会員）は、
その保存カードに対して**注文と同時に決済をかけられる**。お客様の操作は「注文する」の1タップだけ。
スタッフの会計操作もゼロ。**未収も発生しない。**

### 2-2. 成立に必要な3条件

| 条件 | 内容 | 対応 |
|---|---|---|
| **① カードが保存されていること** | 月会費カード払いの会員は保存済み。**現金・口座振替の会員は保存されていない** | 未保存の会員は§2-4のフォールバックへ |
| **② 同意（規約）** | 「ポータルからの注文は、登録カードから自動で決済されます」を**利用規約と入会フォームの同意事項に追加**。既存会員にも周知が要る | **9/2前にやるべきユーザー作業**。文案はこちらで用意する |
| **③ 手数料を許容** | 対面 **2.5%**（SMB申請が条件）に対し、保存カード決済は **3.6〜3.75%**。500円のドリンクで**差は6円**／月1,000杯でも月6,000円 | スタッフの手間ゼロ・未収ゼロと引き換えなら**許容範囲**と判断 |

### 2-3. 注文から会計までの流れ

1. 来店中モードで「注文する」→ メニュー（Squareカタログ同期・**会員価格を自動適用**）
2. 数量を選んで送信 → **その場で登録カードに決済**
3. お客様の画面に「決済しました ¥550」＋**打席番号**を表示
4. **受付iPadの電子伝票に、決済済みの注文として並ぶ**（音つき通知）
5. スタッフが作って持っていき「**提供済み**」を押す
6. Money OS に自動計上（既存のWebhook経路。**店内飲食として分類できるよう振り分けを追加**）

### 2-4. フォールバック（必ず用意する）

- **カード未保存の会員** → 注文画面に「この注文は退店時のお会計になります」と明示し、
  電子伝票に**未決済**として並ぶ。スタッフが退店時にiPadのSquareで会計
- **決済失敗（限度額・期限切れ）** → 注文自体は通し、**未決済として伝票に出す**。
  注文を止めない（お客様の前で失敗させない）。あわせてポータルに「カードの更新をお願いします」を出す
- **誤注文の取消** → 提供前ならお客様側から取消可（返金はSquareのrefund）。提供後はスタッフ操作のみ

### 2-5. 「退店時にまとめて引き落とす」案について

ご提案の第2案（退店時にスタッフが「登録のカードから引き落としておきますね」）も可能ですが、
**注文時に決済してしまうほうが全面的に良い**と考えます。理由：

- スタッフの声かけと操作が**毎回発生する**（手間を消したいという目的に反する）
- **飲み逃げ・言い忘れの未収が発生しうる**（注文時決済ならゼロ）
- お客様の体感が「注文したら届く」で完結する（会計の記憶が残らない＝また頼みやすい）

→ **注文時決済を基本、カード未保存の人だけ退店時会計**、という組み合わせにします。

## 3. 会員証QRは固定式で ─ ただし2つ条件をつけます

ご判断のとおり**固定式**でいきます。スクリーンショットを撮ってまで悪用する人は稀、という読みは妥当です。
ただし、**自動決済を入れる以上、なりすましの被害額が0円ではなくなる**ので、次の2点は必ず入れます。

**① QRの中身を「会員番号」にしない**
`F0001` のような連番は、**他人が推測して自分でQRを作れてしまいます**。
中身は**推測できないランダムなID**（数字＋英大文字）にし、会員番号とは別に持ちます。
万一漏れた会員は、ポータルの設定から**QRを再発行**できるようにします。

**② QRでできるのは「チェックインだけ」。注文はポータルのログインからのみ**
こう分けておけば、QRのスクショが流出しても被害は
「知らない人に自分の名前でチェックインされる」程度で止まり、**カードから引き落とされることはありません。**

**なお、固定式でも「スマホを開く習慣」は成立します。**
注文もカルテも予約もポータルの中にしかないので、開く理由は残るためです。
（当初の回転式推奨は「QRしか価値がない」場合の話でした。ポータルを作るなら固定で問題ありません）

## 4. 電子伝票（受付iPad）

ご指摘のとおり、これは**会員のモバイルオーダーと口頭注文を1つに集約する画面**として作ります。
Squareの画面とは別に、iPadのブラウザで開く自社画面です。

**画面（打席順に並ぶ1枚）**

| 表示 | 内容 |
|---|---|
| 打席 | A / B / C ・ 会員名（チェックイン済みなら自動）／ビジターは「ビジターB」等 |
| 品目 | 品名・数量・注文時刻 |
| 会計状態 | **決済済み**（自動決済）／**未決済**（退店時会計・ビジター） |
| 操作 | **提供済み** ／ **品目を追加**（口頭注文） ／ 取消 |

- **口頭注文もここに入れる。** 会員の伝票に追加すればカード決済、ビジターは未決済のまま溜めて退店時にSquareで会計
- **通知**：iPadのブラウザが前面にあれば音とバナー。**バックグラウンドでも取りこぼさないよう、公式LINEのスタッフ通知にも同時に飛ばす**（送信基盤は既にある）
- ビジターの伝票は**打席単位で立てる**（名前が要らない）

## 5-2. チェックイン完了の見せ方（ご提案を採用）

「チェックインしました。あなたの打席は◯◯です」を出す ─ **採用します。**
これは親切なだけでなく、**打席番号を口頭で伝える手間がなくなる**ので、スタッフ側の実利も大きいです。
**2つの画面に同時に出します。**

**① 受付PC（お客様側を向いている画面）**

```
      ✓ チェックインしました
        山田 太郎 様
        打席 A ／ 12:00 - 13:00
        ─────────────────
        入会後3回目のご来店です      ← 声かけカード（§8-1）
```
3秒ほどで待機画面に戻ります。

**② お客様のスマホ（ここが肝）**

QRを表示していた画面が、**そのまま自動で「来店中モード」に切り替わります。**
お客様は何も操作しません。QRをかざす → 顔を上げる → 手元の画面がもう変わっている、という体験です。

```
      ✓ チェックインしました
        打席 A ／ 13:00まで
      ┌──────────────┐
      │   A打席から注文する    │   ← そのまま注文に入れる
      └──────────────┘
        本日のレッスン 14:00 安東コーチ
```

- 実装は、QR表示画面が数秒おきにチェックイン状態を見て切り替えるだけ（軽い）
- **予約なしのフリー来店で打席が未定のとき**は「スタッフが打席をご案内します」と表示し、
  スタッフが打席を割り当てた瞬間にスマホの表示が更新されます

**この切り替えが、実は習慣化の中心です。** かざした直後に画面が変わって注文ボタンが出るので、
「スマホを開く → 注文する」が1回の動作の中でつながります。

## 6. 打席QR ─ **会員とビジターで入口を分けない**

### 6-1. ご懸念への回答：できます。しかも、それが正しい設計です

> 会員さんも間違えてビジター用QRを読んでしまうことが考えられる。
> 会員が読んだら、いつものポータルが開くようにできるか？

**できます。そして「会員用QR」と「ビジター用QR」を分けないのが正解です。**

打席に貼るQRは **`my.frankgolf.jp/bay/A` という1本のURL**にします。
読んだ人が誰かは、**開いた瞬間にログイン状態（cookie）で自動的に判別**されます。

| 読んだ人 | 何が起きるか |
|---|---|
| **ログイン済みの会員** | **いつものポータルが開く。**「A打席から注文」がセットされた状態。**会員価格・登録カードで決済** |
| **未ログイン（ビジター／セッション切れの会員）** | その場でビジター注文画面。名前も登録も不要。A打席の伝票に溜まり**退店時会計** |

**QRが1種類なので、そもそも「間違えて読む」ということが起きません。**
貼るステッカーも1打席1枚で済み、お客様に説明も要りません。

### 6-2. 未ログインの会員をどう会員に戻すか

セッションが切れている会員が読むと、ビジター画面に落ちます。ここは**実利で誘導**します。

> **会員の方はログインすると会員価格になります** → ［ログイン］

値段が違うので、これが一番効きます。一度ログインすれば以降はそのままです。

**保険：**それでもビジターとして注文された場合、受付の電子伝票に「A打席・未決済」として出ます。
スタッフが持っていくときに会員だと分かれば、**伝票から会員に紐付け直せる**ようにします（会員価格に補正・カードへ付替え）。

### 6-3. 注意点：PWAとブラウザでログインが別扱いになることがある

ホーム画面に追加したポータル（PWA）でログインしていても、
**QRから開いたブラウザ側では未ログイン扱いになる**ことがあります（iPhoneで起こりやすい）。
対策は §6-2 と同じで、ブラウザ側でも一度ログインしてもらえば以降は続きます。
入会時の案内で「**ホーム画面に追加**」と「**一度ログインしておく**」の両方を済ませておくのが確実です。

### 6-4. ビジターの扱い（第一弾）

ご判断どおり、**第一弾はスタッフが電子伝票に手入力**でも回ります。
ただし打席QRは**印刷して貼るだけ**なので、Phase 2 で一緒に出してしまうのが得だと考えます
（ビジターの注文が少ないとしても、会員にとっての「打席番号を選ばなくていい」価値のほうが大きいため）。

## 8. 追加アイデア

### 8-1. 受付画面に「声かけカード」を出す ★**採用決定**

QRをかざした瞬間、スタッフ側に**その人に声をかけるネタ**を1〜2行出します。

- 「入会後**3回目**のご来店」
- 「前回から**21日**空いています」
- 「今月がお誕生月」
- 「レッスン枠が**14時から**あります」

データは全部すでにあります。**退会予防に一番効くのは「名前を呼んで一言かける」**ことで、
それをシステムが毎回お膳立てできる形にします。開発コストはほぼゼロです。

### 8-2. 打席にQRステッカーを貼る ★**採用決定** → 設計は §6 へ

### 8-3. 「前回と同じ」ワンタップ

滞在中の2杯目は、メニューを見せずに**「前回と同じ（アイスコーヒー）」の1ボタン**で出します。
客単価に直結する割に、実装は非常に軽いです。

### 8-4. チェックインとレッスンを繋ぐ

レッスン予約がある日にチェックインすると、ポータルが自動で「**本日のレッスン 14:00 安東コーチ**」を表示。
レッスン終了後、**カルテが書かれたらポータルに通知**が出るようにします。

Lesson OS が稼働しなかった最大の理由は「**書いても生徒に届かない**」ことでした。
ポータルができると、この穴がそのまま塞がります。**チェックイン導入の副産物として一番価値が大きい**部分です。

### 8-5. 来店スタンプ（紙のスタンプカードを不要にする）

チェックインが自動でカウントするので、「**5回来店で1杯サービス**」のような施策が
紙もスタッフの押印もなしで回ります。プレオープン期の再来店づくりに効きます。

### 8-6. 自動チェックアウト＋お礼

予約終了時刻＋30分でチェックアウト扱いにし、滞在時間を記録。
退店後に**お礼＋次回予約ボタン**を1通送ります（送信基盤は既にあります）。

## 9. 変わらない注意点

- **手動チェックインは必ず残す**（スマホ忘れ・ログイン不能）。無いと現場が止まる
- **卓上リーダーは何でも勝手に読む** → 「自社トークン形式でなければ捨てる」判定を受け口に置く
- トークンの文字種は **数字＋英大文字のみ**（キーボード配列で化けない／仮想COMでも安全）
- **会員の導線を増やすときは必ず `frunk_members` に入るか確認する**
  （過去に、台帳に無い仮会員番号を発行してWeb登録者が100%予約できなかった事故がある）
- **店舗スコープはサーバー側で検証**（UIで隠すだけにしない）
- 受付画面に出す個人情報は**氏名・プラン・打席・注意事項まで**（生年月日/住所は出さない）
