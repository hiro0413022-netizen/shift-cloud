# Inventory OS — 在庫・棚卸（正典）

DECISIONS #96 / migration `0086_inventory_os.sql` / アプリ `apps/inventory-os`

---

## 1. なぜ作ったか

物販在庫は `202606_ゴルフウィング在庫リスト.xlsm`（VBA付き）で管理されていた。移行時点の実態:

| 項目 | 値 |
|---|---|
| 品番数 | 362 |
| 最新棚卸（2026-06-30）の点数 | 1,259 |
| 仕入単価ベースの在庫金額 | 約 277万円 |
| 棚卸履歴 | 2025-12〜2026-06 の7ヶ月分 |
| 品目 / メーカー | 22種 / 36社 |

このエクセルには構造上の限界が4つあった。

1. **棚卸台帳であって在庫台帳ではない。** 月1回の実地カウントの記録しかなく、入荷・販売による増減が追えない。だから「なぜ減ったか」が分からない。
2. **月ごとに4列（確認日・時間・担当・数量）が横に増える。** 7ヶ月で43列。12ヶ月で91列に達し、いずれファイル分割が必要になる。
3. **保管場所が95件（26%）空欄。** 棚卸のとき「どこにあるか」を思い出しながら探すことになる。
4. **数量ゼロのまま残っている品番が58件。** 扱いをやめたものが混ざったまま毎月数えられている。

さらに golfwing（発注・入荷管理）と完全に分断していて二重入力になっていた。
golfwing の ROADMAP にある **LP-001「在庫管理モジュール統合」** がまさにこの課題。

## 2. 設計 — 3層分離

エクセルが1枚で兼ねていたものを、役割ごとに3つに分ける。

| 層 | テーブル | 役割 |
|---|---|---|
| マスタ | `inv_items` | 品番362件。管理番号・品目・メーカー・仕様・保管場所・定価・仕入単価・**適正在庫** |
| 台帳 | `inv_movements` | 入出庫1件＝1行。入荷／販売／工房使用／棚卸調整／破損／店舗間移動。**エクセルに無かった層** |
| 棚卸 | `inv_count_sessions` + `inv_counts` | 棚卸1回＝1セッション、1品番＝1明細。エクセルの横持ちを縦持ちに変換 |

補助として `inv_codes`（品目・メーカーの略号表。エクセルの「コード表」シート相当）。

### 理論在庫の定義

```
理論在庫 = 直近の「確定した」棚卸の数量 + その棚卸日より後の inv_movements の合計
```

ビュー `inv_stock` がこれを計算する。全期間の movements を積む方式にしていないのは、
移行時点で過去の入出庫データが存在しないため（積んだら在庫が全部ゼロになる）。

棚卸を確定すると、実地と理論の差が `kind='adjust'` の movements として自動起票される。
**締めた瞬間から理論在庫が実地に一致する**。money-os の金種棚卸（`mon_cash_count`）とまったく同じ思想。

### 管理番号

`品目略号-メーカー略号-連番`（例 `DRC-TM-001` = ドライバークラブ / テーラーメイド / 001）。
エクセルのVBAフォームが持っていた採番と重複チェックは、DB関数 `inv_next_code()` と
`inv_codes` の unique index に移した。連番をDBで採るので、二人が同時に登録しても衝突しない。

## 3. テーブル一覧

| テーブル | 用途 | 備考 |
|---|---|---|
| `inv_codes` | 品目・メーカーの略号 | `(company_id, kind, abbr)` と `(company_id, kind, name)` が一意 |
| `inv_items` | 品番マスタ | `status='discontinued'` で棚卸対象から外す |
| `inv_movements` | 入出庫 | 入庫は `qty` 正・出庫は負。`(source_app, source_id)` が一意＝二重計上の最終防衛 |
| `inv_count_sessions` | 棚卸1回 | `(company_id, store_id, counted_on)` が一意 |
| `inv_counts` | 棚卸明細 | `(session_id, item_id)` が一意 |
| `inv_stock`（view） | 理論在庫 | `needs_reorder` が true の品番＝発注候補 |
| `inv_monthly_valuation`（view） | 月次の棚卸資産・仕入・売上原価 | money-os / report-os が読む |

RLSは有効・ポリシーなし＝**service_role専用**（本リポジトリの標準形 #65）。
DB関数 `inv_next_code` / `inv_close_count` は service_role に EXECUTE を付与済み。

## 4. 画面（apps/inventory-os・port 3012）

| パス | 内容 | 権限 |
|---|---|---|
| `/` | 在庫状況。品番数・点数・在庫金額・発注候補・保管場所別・在庫ゼロ品番 | 全員 |
| `/count` | 棚卸の一覧と開始 | 全員 |
| `/count/[id]` | **棚卸シート（iPad用）** | 入力=全員 / 確定=manager |
| `/items` | 品番マスタ一覧・検索 | 全員 |
| `/items/new` | 新規品番登録＋コード表への追加 | manager |
| `/items/[id]` | 品番詳細（入出庫履歴・棚卸の推移）＋編集 | 閲覧=全員 / 編集=manager |
| `/movements` | 入出庫の記録と履歴 | 記録=manager |

### 棚卸シートの設計意図（iPad前提）

現場のスタッフが棚の前に立って数える道具なので、次の4点を優先した。

- **保管場所で絞り込む。** 棚の前に立ったらその場所の品番だけが見える。タブに `12 / 37 ✓` の進捗が出る
- **前回値を大きく出す。** 同じならタップ1回（「同じ」ボタン／＋−）で確定、違うときだけ数字を打つ
- **入力のたびに自動保存（400msデバウンス）。** 「保存ボタンを押し忘れて全部消えた」を起こさない
- **タップ領域は48px。** 手袋でも押せるサイズ

締める前に「残りN件を『前回と同じ』で埋める」ボタンがある。
362行を上から舐める作業が、**数の変わった品番だけ触る**作業になる。
実データ上、月次の変化は30〜90品番（全体の8〜25%）しかない。

### 権限

| ロール | 条件 | できること |
|---|---|---|
| `manager` | `view_hq` または `manage_inventory` | マスタ編集・棚卸の確定・入出庫の記録 |
| `counter` | `use_inventory` | 棚卸のカウント入力（確定はできない） |

権限データはGenesis / Shift Cloud と共通（同一DB）。

## 5. 他システムとの連携

### golfwing（発注・入荷）→ 入庫

golfwing は**別のデータベース**で動いているためDBトリガーでは繋がらない。
入荷を確定した側から API を叩いてもらう。

```
POST /api/v1/movements
Authorization: Bearer $INVENTORY_API_TOKEN

{
  "source_app": "golfwing",
  "kind": "receipt",
  "occurred_on": "2026-07-30",
  "lines": [
    { "code": "GR-IO-001", "qty": 12, "unit_cost": 754, "source_id": "<receipt_items.id>" }
  ]
}
```

- 突き合わせキーは **Inventory OS の管理番号**。golfwing 側の商品マスタにこれを持たせてから有効化する
- `source_id` を入れておけば再送しても増えない（`uq_inv_mov_source`）
- 見つからない品番はエラーにせず `unmatched` として返し、残りは通す（1品エラーで入荷全体を止めない）
- `GET /api/v1/movements?code=...` で管理番号の存在と現在庫を確認できる

**注: golfwing の商品コードマスタは未整備で、ワークス発注も同じ理由で止まっている（REDESIGN_2026-07 §在庫ループ）。
連携を有効化する前にそこを解消する必要がある。**

### money-os → 売上原価・粗利

同一DBなのでビューで繋ぐ。`inv_monthly_valuation` が月次で返す:

| 列 | 内容 |
|---|---|
| `opening_value` | 期首在庫（前月末の確定棚卸の評価額） |
| `closing_value` | 期末在庫 |
| `purchase_value` | 当月仕入（`kind='receipt'` の原価合計） |
| `cogs` | 売上原価 ＝ 期首 + 仕入 − 期末（三分法） |
| `average_value` | 平均在庫（在庫回転日数の分母） |

**棚卸が無い月は行が出ない。推計はしない**（嘘の数字をPLに流さないため）。

移行直後は `purchase_value` が全月ゼロなので `cogs` が実態とずれる（2026-02は −150,263 と負になる）。
これは異常ではなく、**入荷を記録していなかったという事実がそのまま出ている**状態。
入出庫の記録を始めた月から正しくなる。

### report-os → 物販セクション

`docs/modules/report-os/SYSTEM.md §4` の宿題「物販の入れ物が未整備」がここで埋まる。
在庫回転日数 = `average_value / cogs × 日数`、死蔵在庫 = 直近2回の棚卸で数量が動いていない品番。

## 6. エクセルからの移行

`scripts/inventory/excel-to-inv.py` が `202606_ゴルフウィング在庫リスト.xlsm` を読んで
シードSQL（`scripts/inventory/seed_202606.sql`）を生成する。原本も同ディレクトリにアーカイブ済み。

移行方式:

- 品目・メーカーは管理番号（`CAT-MK-nnn`）から `inv_codes` への join で復元（原本362行すべてで一致を確認済み）
- 棚卸は最古の2025-12だけ全量、以降は「前月をコピー → 消えた品番を削除 → 増えた品番を挿入 → 変わった数量をUPDATE」の差分方式
- 担当・時刻はセッション内の最頻値を既定とし、それ以外の品番だけ明示的に上書き

**検証:** 7セッション × 全品番の `(管理番号, 数量)` を連結したMD5が原本と完全一致（2,259レコード）。
品目略号ごとの件数・合計数量の突合も差分ゼロ。

移行分のセッションは `theoretical` / `diff` が null。
当時は入出庫台帳が無く理論在庫が存在しなかったため、`inv_close_count` を通さず
直接 `status='closed'` で投入している（過去分に adjust を起票しない）。

## 7. 運用上の注意

- **「今日」はJSTで解決する。** サーバー（Vercel）はUTCなので `lib/jst.ts` を必ず使う（#73）
- **`adjust` は棚卸の確定でのみ起票される。** 画面からもAPIからも直接は作れない
- **棚卸を確定できるのは manager だけ。** 確定すると差異が台帳に載り、以降の理論在庫の起点になる
- **保管場所を埋めると棚卸が速くなる。** 未設定の品番は「（保管場所 未設定）」タブにまとまる
- **扱いをやめた品番は `discontinued` に。** 棚卸画面から消える（削除はしない＝過去の棚卸は残る）
