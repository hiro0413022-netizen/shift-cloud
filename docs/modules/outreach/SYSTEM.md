## 1. これで一周した

```
①拾う（毎朝5時/8時）→ 採点 → デモ自動生成
   ↓
②送る（毎日10時）→ 届いた/開かれた を計測
   ↓
③開封＝ホットリード → Genesisホームに「開封直後の架電」が出る（#95）
   ↓
返信 → info@yozan-group.jp（Gmail）
```

人の稼働が要るのは、返信が来てからの商談だけになる。

## 2. どこで動くか

| | |
|---|---|
| 送信 | `apps/demo-sales/src/app/api/cron/outreach/route.ts`（Vercel Cron・毎時） |
| 送信時刻 | `out_settings.send_hour_jst`（既定10時JST）。cronは毎時叩き、その時刻の回だけ送る＝時刻変更にデプロイが要らない |
| 配信結果 | `/api/webhooks/resend`（Resendが叩く） |
| 配信停止 | `/unsubscribe/[token]`（ログイン不要・開いた時点で停止） |
| 画面 | demo-sales `/outreach` |

## 3. 送ってよい条件（`src/policy.ts`）

**このパッケージで最も壊してはいけない場所。** メールは取り消せないので、DBに触らない純粋関数にして
テストで固定し、送信側は必ずここを通す（`server.ts` が唯一の呼び出し元）。

判定は「送ってよい理由が揃っているか」で書いてある。除外条件を並べる書き方だと、
条件を1つ足し忘れたときに**送れてしまう方向**に倒れるため。

送信できるのは、次が**すべて**成り立つときだけ:

1. 送信が有効（`enabled`）かつ自動停止中でない
2. メールアドレスがあり、**出どころが `site`**（＝先方サイトに公表されていた）
3. 「営業お断り」の表示が無い
4. 抑止リスト（アドレス・ドメイン）に無い
5. その先へまだ1通も送っていない
6. **デモが完成している**（見せるものが無いメールはただの売り込み）
7. Web現況スコアが下限以上（既定55点）
8. その日の上限に達していない

### なぜ「サイトでの公表」に限るのか

特定電子メール法3条1項3号は、**自己のメールアドレスを公表している営業者**への送信を同意なしで認める。
名簿サイトやGoogle Places から得たアドレスは、公表主体が先方本人とは限らないので根拠にならない。
だから `dms_prospects.email_source` に出どころを、`email_page_url` に確認したページを残し、
`site` 以外は送信対象から外す。**推測でアドレスを組み立てること（info@ドメイン等）は絶対にしない。**

## 4. 止めるための構造

送る仕組みと**同時に**作った。後から足すものではない。

- **ウォームアップ**: 初日10通、1日10通ずつ増、上限で頭打ち（`dailyCap`）。新しい送信元から急に大量送信すると迷惑メール判定される
- **自動停止（キルスイッチ）**: 直近100通で「宛先不明8%超」または「迷惑報告2件」で自動停止。
  放置すると送信ドメインの信用が壊れ、**会社の普段のメールまで届かなくなる**ので、人が気づくのを待たない
- **手動停止**: `/outreach` の「いますぐ止める」
- **抑止リスト**: 配信停止・バウンス・苦情を自動で積む。ドメイン単位も可
- **1営業先1通**: `out_messages` の部分ユニーク索引で構造的に担保（アプリの条件分岐に頼らない）
- **記録が先・送信が後**: `queued` 行を作ってから送る。逆にすると記録前に落ちたとき二重送信になる

## 5. 法定表示（`src/compose.ts`）

特定電子メール法4条は、送信者の氏名・名称、住所、受信拒否の通知先の表示を義務づけている。
これを**テンプレート本文に書かせない**。書き忘れた文面が1つでも混ざった瞬間に違法になるため、
`composeEmail` が `companies.settings.invoice`（#99で登録済み）から機械的に付ける。テンプレート側で消せない。

住所が未設定なら**送信そのものを中止**する（黙って住所なしで送らない）。

`List-Unsubscribe` / `List-Unsubscribe-Post`（RFC 8058）も付ける。Gmail等が一覧上に「配信停止」ボタンを出し、
押しやすい停止導線があるほど**迷惑メール報告が減る**＝ドメインの信用が守れる。

## 6. 送受信をどこで見るか

| 見たいもの | 場所 |
|---|---|
| 誰にいつ何を送ったか・届いたか・開かれたか | demo-sales `/outreach` の送信ログ |
| 送らなかった先とその理由 | 同画面（「送らずに内容を確認」で件数と理由の内訳） |
| 配信停止・バウンス・苦情 | 同画面「送らない先」 |
| **先方からの返信** | **info@yozan-group.jp → hiro0413022@gmail.com（転送済み）**。Gmailで読む |
| デモを開いたか（ホットリード） | Genesisホームの判断フィード（@yozan/track #95） |

返信をシステム側に取り込んでいないのは、既存の受信経路（info@ → Gmail転送 → CEO Inbox）があり、
新しい受信経路を増やすと二重管理になるため。返信率が上がったら `replied_at` の自動記録を検討する。

## 7. 環境変数

| Key | 場所 | 無いとどうなるか |
|---|---|---|
| `RESEND_API_KEY` | demo-sales | 送信されず `canceled` で記録される（1件目で打ち切り） |
| `RESEND_WEBHOOK_SECRET` | demo-sales | 署名検証をスキップ（未知の provider_id は無視するので被害は限定されるが、設定推奨） |
| `OUTREACH_MIN_SCORE` / `OUTREACH_DELAY_MS` / `OUTREACH_BUDGET_MS` | demo-sales | 既定値（55 / 3000 / 200000） |

送信元・返信先・上限・時刻はenvではなく **`out_settings`（画面から変更）**。運用で変えるものをenvに置くと再デプロイが要るため。

## 8. 壊しやすい点

- **`policy.decideSend` を通さない送信経路を作る** → 何のための判定か分からなくなる。送信は `server.ts` 一本
- **`email_source` を site 以外にも広げる** → 法的根拠が消える。広げたくなったら法務判断が先
- **本文テンプレートに会社情報や配信停止リンクを手書きする** → compose と二重になり、片方だけ古くなる
- **`/unsubscribe` `/api/webhooks` を middleware の公開プレフィックスから外す** → 停止できないメールを送ることになる（最悪の事故）
- **ウォームアップ上限を最初から50にする** → 迷惑メール判定で全部届かなくなる。`daily_cap_max` は最終値であって初日の値ではない
- **自動停止を解除して原因を直さずに再開する** → 同じ理由でまた止まる。`paused_reason` を読んでから解除する
